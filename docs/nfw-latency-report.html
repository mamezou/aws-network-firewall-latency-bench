Phase 2 の p99 が 3.500 ms と突出して高い。ステートフル処理による初回フロー検査コストが尾部レイテンシーに影響している。
⚠ Phase 1 と Phase 2 の p50 逆転について:
Phase 1 (0.900 ms) > Phase 2 (0.700 ms) という結果はステートフルルールの方が速いことを意味しない。 nping の RTT 分解能は 0.1 ms 単位であり、差分 0.2 ms はツールの最小刻み幅 2 つ分に過ぎない。 本来ステートフル処理のコストはゼロより大きいため、この差は測定誤差・タイミングノイズの範囲内と判断する。 厳密な比較には複数セッションの平均化と高分解能ツール（hping3 など）が必要。

⚠ この数値の読み方に注意:
これは 単一 TCP フロー の計測値であり、「NFW を入れるとスループットが半減する」という一般則ではない。 iperf3 のデフォルト（-P 1）は単一フローのため、NFW の分散処理ボリュームとは異なる条件になる。 本番環境では複数フローが並走するため、iperf3 -P 4 等のマルチフロー計測で大きく改善する可能性がある。 スループット要件がある場合は、実際のトラフィックパターンで個別に検証することを強く推奨する。
5考察・まとめ
  • ステートレスルールのみ（Phase 1）でも TCP RTT p50 で +0.8ms の追加レイテンシーが発生。 NFW エンドポイントを経由するだけで生じる固定コストであり、ルールの複雑さに依存しない。
  • ステートフルルール追加（Phase 2）は p50/p95 が微減（nping 分解能 0.1ms 以内の差のため測定誤差の範囲内、有意差なし）。ただし p99 が 3.5ms と大幅に増加。 ステートフル処理による初回フロー検査コストが尾部レイテンシーに影響している。
  • TLS 検査（Phase 3）の TCP RTT は Phase 1/2 と同程度。追加の TCP レイテンシーはほぼなし。 ただし TLS ハンドシェイクが +1.7ms (p50)。 AWS 公式 Security Blog の「シングルミリ秒台 (single-digit milliseconds)」という記述を自前計測で裏付けた点は本ベンチマークの主要な成果。
  • スループットは単一フロー計測で約半減（9.5→4.8 Gbps）。 ただしこれは iperf3 -P 1（単一フロー）の結果であり、マルチフロー環境での値ではない。 本番トラフィックでの影響は個別計測が必要（iperf3 -P 4 等を推奨）。
口頭説明用ワンライナー:
「実測では、ステートレスのみで +0.8ms、ステートフル追加でも p50 は同程度（p99 は +3.5ms）、 TLS 検査の TCP RTT への追加影響はほぼなし、TLS ハンドシェイクは +1.7ms でした。」

6注意事項
  • nping の RTT 精度は 0.1ms 単位のため、p50/p95 の分解能に限界がある（最小分解能 0.1ms）。
  • 単一フロー計測のため、マルチフロー環境での結果は異なる場合がある（スループットは特に影響が大きい）。
  • 計測は単一の計測セッション（各フェーズ1回）のため、統計的信頼性には限界がある。複数回の計測による平均化が推奨される。
  • NFW エンドポイントや EC2 インスタンスのリソース状況によって結果が変動する場合がある。
